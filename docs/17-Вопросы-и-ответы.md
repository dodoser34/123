## Общие вопросы

### 1. Что это за проект?

**Коротко:** интернет-магазин корейской косметики и лечебных трав «K-Beauty | C-Health» для Казахстана: каталог, корзина, оформление заказа, оплата через Kaspi, личный кабинет, отзывы и админ-панель для владельца.

**Подробнее:** проект состоит из трёх частей: сайт (фронтенд), сервер с базой данных (бэкенд) и настройки для публикации в интернете (деплой). Сайт может работать и без сервера — в демо-режиме, для показа.

**Где посмотреть:** [раздел 1](01-Что-это-за-проект.md), `README.md`.

### 2. Какие технологии использованы?

**Коротко:** фронтенд — HTML, CSS и JavaScript без фреймворков; бэкенд — Python и FastAPI; база данных — PostgreSQL; запуск — Docker и Nginx; HTTPS — Let's Encrypt.

**Подробнее:** для работы с базой — SQLAlchemy (ORM) и Alembic (миграции), для паролей — bcrypt, для входа через Google — OAuth 2.0, для тестов — pytest и встроенный тестировщик Node.js.

**Где посмотреть:** [раздел 16, п. 2](16-Как-это-работает.md).

### 3. Почему фронтенд без фреймворка (React, Vue)?

**Коротко:** для магазина такого размера фреймворк не нужен: обычные файлы открываются сразу, без сборки, быстро грузятся и их проще поддерживать.

**Подробнее:** вместо фреймворка — свой небольшой порядок: загрузчик `js/app.js` подключает файлы, хранилище `App.db` — единая точка работы с данными, компоненты (шапка, карточка, окна) — отдельные файлы. Это даёт те же преимущества (разделение кода), но без лишних зависимостей.

**Где посмотреть:** `frontend/js/`, [раздел 2](02-Как-устроен-сайт.md).

### 4. Какая у проекта архитектура?

**Коротко:** клиент-сервер. Браузер (клиент) показывает страницы и отправляет запросы, сервер (API) проверяет права, считает суммы и работает с базой данных. Сервер разделён на слои: ядро, база, проверка данных, сервисы, маршруты.

**Подробнее:** слои сервера: `core/` (настройки, безопасность), `db/` (таблицы), `schemas/` (проверка входящих данных), `services/` (оплата, письма), `api/` (адреса запросов). Каждый слой отвечает за своё — так проще искать ошибки и менять код.

**Где посмотреть:** [раздел 12](12-Архитектура.md) — схемы.

### 5. Что такое API и как сайт общается с сервером?

**Коротко:** API — «окошко выдачи» сервера. Сайт отправляет запрос по адресу (например, `POST /api/orders` — оформить заказ), сервер отвечает данными в формате JSON.

**Подробнее:** используется подход REST: адрес обозначает, *что* (товары, заказы), а метод — *что сделать* (GET — получить, POST — создать, PUT/PATCH — изменить, DELETE — удалить). Документация всех адресов создаётся автоматически: `/api/docs`.

**Где посмотреть:** `backend/app/api/routers/`.

### 6. Почему FastAPI?

**Коротко:** быстрый современный фреймворк на Python, который сам проверяет входящие данные по описанию и сам создаёт документацию API.

**Подробнее:** работает асинхронно (может обслуживать много запросов одновременно, пока ждёт базу или почту), правила для данных описываются один раз — в схемах.

## База данных

### 7. Почему PostgreSQL и какие в ней таблицы?

**Коротко:** PostgreSQL — надёжная бесплатная база, стандарт для магазинов. Таблицы: пользователи, сессии, коды из писем, категории, товары, отзывы, голоса за отзывы, заказы, настройки сайта.

**Подробнее:** товар хранит важные поля (цена, остаток, статус) отдельными колонками, а описание, состав и фото — в поле JSON, поэтому новые разделы карточки не требуют менять базу.

**Где посмотреть:** `backend/app/db/models.py`, [раздел 12 — «База данных»](12-Архитектура.md).

### 8. Что такое ORM и миграции?

**Коротко:** ORM (SQLAlchemy) позволяет работать с базой через код на Python, а не писать SQL-текст вручную. Миграции (Alembic) — это записанная история изменений структуры базы, которая применяется автоматически.

**Подробнее:** при обновлении сайта сервер сам выполняет `alembic upgrade head` и аккуратно меняет таблицы, не теряя данных. Вернуться назад можно командой `downgrade`.

**Где посмотреть:** `backend/migrations/versions/`.

### 9. Как база защищена от неправильных данных и потери?

**Коротко:** в самой базе стоят ограничения (цена ≥ 0, оценка 1–5, только известные роли и статусы), база закрыта от интернета, а раз в сутки делается резервная копия.

**Подробнее:** копии хранятся 14 дней в `deploy/backups/`, восстановление — одна команда (`pg_restore`). Долгие запросы прерываются через 15 секунд, число подключений ограничено.

**Где посмотреть:** [раздел 11 — «База данных на сервере»](11-Бэкенд-и-деплой.md).

## Аккаунты и безопасность

### 10. Как хранятся пароли?

**Коротко:** пароли не хранятся вообще — хранится их хеш bcrypt с солью. Из хеша пароль восстановить нельзя.

**Подробнее:** хеш — «отпечаток» пароля. При входе введённый пароль снова хешируется и сравнивается. Соль — случайная добавка, из-за которой одинаковые пароли дают разные хеши. bcrypt намеренно медленный (12 раундов), поэтому подбор занял бы годы.

**Где посмотреть:** `backend/app/core/security.py`.

### 11. Как сайт «помнит», что пользователь вошёл?

**Коротко:** после входа сервер выдаёт случайный токен; браузер прикладывает его к каждому запросу. В базе хранится не сам токен, а его SHA-256-отпечаток.

**Подробнее:** токен действует 30 дней. Выход удаляет сессию, смена пароля завершает все остальные сессии. Используется заголовок `Authorization: Bearer`, а не cookie — поэтому атака CSRF не работает.

**Почему не JWT?** Сессии в базе можно отозвать мгновенно (выход, блокировка, смена пароля), а JWT действует до окончания срока.

### 12. Как работает подтверждение почты?

**Коротко:** при регистрации на почту приходит 6-значный код; пока его не введут, войти нельзя.

**Подробнее:** код живёт 10 минут, ввести можно 5 раз, повторно отправить — раз в минуту. В базе хранится не код, а его HMAC-отпечаток.

**Где посмотреть:** `backend/app/api/routers/auth.py`.

### 13. Как работает вход через Google?

**Коротко:** по стандарту OAuth 2.0: сайт отправляет на страницу Google, Google подтверждает личность и возвращает на сервер почту и имя. Пароль от Google магазин не видит.

**Подробнее:** параметр `state` подписывается секретным ключом сервера — так нельзя подделать ответ. Принимается только почта, которую Google отметил подтверждённой. Чтобы включить, в `.env` указываются `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`.

### 14. Где хранятся почта и пароль администратора?

**Коротко:** только в файле `deploy/.env` на сервере — его нет в git, и его не видно с сайта.

**Подробнее:** при каждом запуске сервер создаёт аккаунт администратора или обновляет его пароль из `.env`. Вместо пароля можно хранить его хеш (`ADMIN_PASSWORD_HASH`). Удалить или заблокировать администратора через сайт нельзя. В рабочем режиме сервер не запустится, если пароль короче 12 символов.

**Где посмотреть:** `deploy/.env.example`, функция `ensure_admin` в `backend/app/main.py`.

### 15. Как проверяются права администратора?

**Коротко:** на сервере, при каждом запросе. У пользователя есть роль: «покупатель» или «администратор»; все адреса админки требуют роль администратора.

**Подробнее:** скрытая кнопка на сайте — не защита, поэтому проверка именно на сервере (`api/deps.py`, `admin_user`). Без входа — ответ 401, без прав — 403. Роль нельзя передать в запросе. Это проверяют тесты.

### 16. Как защищено от SQL-инъекций?

**Коротко:** запросы к базе строятся через SQLAlchemy с параметрами — то, что ввёл пользователь, никогда не становится частью SQL-команды.

**Подробнее:** дополнительно все входящие данные проверяются схемами: длина, формат, допустимые символы. Тест пытается войти с паролем `' OR '1'='1` и `DROP TABLE` — вход не проходит, таблицы целы.

**Где посмотреть:** `backend/tests/test_security.py`.

### 17. Как защищено от XSS (внедрения скриптов)?

**Коротко:** три уровня: данные выводятся экранированными, HTML в текстах очищается (остаются только `<b> <i> <br>`), а политика CSP запрещает браузеру выполнять чужие и встроенные скрипты.

**Подробнее:** очистка делается и на сервере (`core/sanitize.py`), и в браузере (`core/texts.js`). Ссылки вида `javascript:` в фото запрещены.

### 18. Как защищено от подбора паролей и DDoS?

**Коротко:** ограничение частоты запросов: например, не больше 5 попыток входа в минуту на один аккаунт и 10 — с одного адреса. Перегрузку отсекает Nginx.

**Подробнее:** два рубежа. Nginx ограничивает запросы и соединения с одного IP и обрывает медленные соединения. Сам API ограничивает попытки входа, отправку писем, регистрации, а также размер запроса (1 МБ). Превышение — ответ 429 «Слишком много попыток».

**Где посмотреть:** `deploy/nginx/security.conf`, `backend/app/core/rate_limit.py`.

### 19. Что такое CSRF и почему сайт от него защищён?

**Коротко:** CSRF — когда чужой сайт заставляет браузер отправить запрос от вашего имени, используя cookie. Здесь вход по токену в заголовке, а не по cookie, поэтому чужой сайт не может его подставить.

**Подробнее:** вдобавок CORS разрешает запросы к API только с адреса самого магазина.

### 20. Какие ещё меры безопасности есть?

**Коротко:** HTTPS, защитные заголовки (CSP, HSTS, запрет встраивания в чужие страницы), проверка типа загружаемых фото по содержимому, секреты только в `.env`, в рабочем режиме сервер не запускается с небезопасными настройками.

**Где посмотреть:** [раздел 15](15-Безопасность.md) — полная таблица и чек-лист.

## Магазин и оплата

### 21. Можно ли подменить цену товара в браузере?

**Коротко:** нет. Браузер отправляет только номера товаров и количество, а цены и сумму сервер берёт из базы.

**Подробнее:** если прислать `price: 1` и `total: 1`, сервер это проигнорирует — это проверяет тест `test_order_amounts_cannot_be_forged`.

### 22. Что будет, если двое одновременно купят последний товар?

**Коротко:** не получится продать больше, чем есть. На время оформления сервер блокирует строку товара в базе, поэтому второй заказ увидит уже уменьшенный остаток.

**Подробнее:** если товара не осталось, он не попадёт в заказ. Отмена заказа администратором возвращает товар на склад.

### 23. Как работает оплата через Kaspi?

**Коротко:** сейчас — перевод на Kaspi владельца: после заказа покупатель видит номер, получателя, сумму и комментарий «Заказ №…», а администратор отмечает «Оплачен», когда деньги пришли.

**Подробнее:** заказ получает статус «Ждёт оплаты» и показывается в личном кабинете с реквизитами. Также есть оплата наличными при получении.

**Где посмотреть:** [раздел 14](14-Платежи.md).

### 24. Как подключить настоящую онлайн-оплату (Kaspi Pay)?

**Коротко:** код уже готов: нужно получить ключи в кабинете Kaspi Pay, вписать их в `.env` и включить `kaspi_pay` в `PAYMENT_METHODS`.

**Подробнее:** сервер создаёт счёт в Kaspi, Kaspi присылает уведомление (webhook) об оплате. Уведомление принимается только с верной подписью HMAC и если сумма совпадает с заказом, а повторное ничего не меняет. Новые способы оплаты добавляются отдельным файлом (шаблон «стратегия»).

### 25. Нужно ли регистрироваться, чтобы пользоваться сайтом?

**Коротко:** нет. Смотреть каталог, товары, отзывы и собирать корзину может любой посетитель. Вход нужен только для оформления заказа, личного кабинета, отзывов и админки.

**Подробнее:** это проверяет `js/core/auth-guard.js` на сайте — с закрытых страниц гость уходит на вход и после входа возвращается обратно — и сам сервер: создать заказ без входа нельзя (ответ 401). Быстрый вход в демо-аккаунты есть только локально и на GitHub Pages.

### 26. Где хранится корзина?

**Коротко:** в браузере покупателя (`localStorage`). На сервер она уходит только при оформлении заказа.

**Подробнее:** так корзина работает мгновенно и сохраняется, даже если закрыть вкладку. Заказы, аккаунты и отзывы хранятся на сервере.

### 27. Как администратор управляет сайтом?

**Коротко:** через админ-панель: товары (добавить, изменить, скрыть, загрузить фото), категории, заказы и их оплата, отзывы (ответить, скрыть), пользователи (заблокировать), тексты сайта и фото страницы «О нас».

**Подробнее:** в «Настройках» есть блок «Готовность к запуску» — показывает, что на сервере настроено (почта, Google, оплата), а чего не хватает.

**Где посмотреть:** [раздел 5](05-Инструкция-по-админке.md).

## Интерфейс

### 28. Как сделана адаптивность под телефоны и большие экраны?

**Коротко:** медиазапросами CSS — правилами «если экран такой ширины, оформить так». Стили разложены по устройствам: телефон, планшет, компьютер, 2K/4K, сенсорные экраны.

**Подробнее:** на телефоне меню прячется в «бургер», фильтры каталога открываются отдельной панелью, кнопки увеличены под палец. Если в системе отключены анимации — сайт их тоже отключает.

**Где посмотреть:** `frontend/css/responsive/`, [раздел 7](07-Адаптивность.md).

### 29. Что такое демо-режим и зачем он нужен?

**Коротко:** режим без сервера: все данные хранятся в браузере. Нужен для показа и согласования дизайна — например, на бесплатном GitHub Pages.

**Подробнее:** переключатель — адрес API в `env.js`. Пустой — демо, указан — работа с сервером. Страницы при этом одинаковые: их код работает с хранилищем, а хранилище само решает, куда писать.

## Запуск и качество

### 30. Как сайт публикуется в интернете?

**Коротко:** на сервере запускается Docker Compose: пять контейнеров — база PostgreSQL, API, Nginx (сайт и HTTPS), продление сертификата, резервные копии. Все настройки — в одном файле `deploy/.env`.

**Подробнее:** HTTPS-сертификат бесплатный от Let's Encrypt и продлевается сам. Есть и вариант без своего сервера — Render (`render.yaml`). Схема базы обновляется сама при запуске.

**Где посмотреть:** [раздел 11](11-Бэкенд-и-деплой.md).

### 31. Где хранятся пароли и ключи, почему их нет в коде?

**Коротко:** в файле `.env` на сервере (или в настройках хостинга). Он внесён в `.gitignore` и никогда не попадает в GitHub.

**Подробнее:** если пароль попадёт в git, его увидит любой, у кого есть доступ к репозиторию, и он останется в истории навсегда. В программе секреты хранятся особым типом (`SecretStr`), чтобы случайно не напечататься в журналах. Для разработки `.env` не нужен — используются безопасные тестовые значения.

### 32. Как проверялась работа сайта?

**Коротко:** 264 автоматических теста плюс проверка в браузере. Тесты запускаются сами в GitHub при каждом изменении.

**Подробнее:**
- **модульные тесты** проверяют маленькие части: маску телефона, подсчёт цены, фильтры;
- **интеграционные** — сервер целиком: регистрация, заказ, оплата, права;
- **тесты безопасности** — инъекции, XSS, перебор паролей, подделку уведомлений об оплате;
- **сквозные (E2E)** — настоящий браузер проходит путь покупателя и администратора.

Сервер проверяется и на SQLite, и на PostgreSQL.

**Где посмотреть:** [tests/README.md](../tests/README.md).

### 33. Что можно улучшить дальше?

**Коротко:** подключить онлайн-оплату Kaspi Pay, уведомления о новых заказах владельцу (Telegram/почта), политику конфиденциальности, аналитику посещений и казахский язык.

**Подробнее:** для большой нагрузки — хранить счётчики лимитов в Redis (сейчас они в памяти процесса), а фото — в облачном хранилище. Всё это не требует переделки — архитектура рассчитана на такие дополнения.

**Где посмотреть:** [раздел 9](09-Ограничения-и-следующие-шаги.md).
