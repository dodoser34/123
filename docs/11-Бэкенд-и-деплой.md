# 11. Бэкенд и деплой

Сайт умеет работать в двух режимах:

| Режим | Где хранятся данные | Когда использовать |
|---|---|---|
| **Демо** (без сервера) | В браузере каждого посетителя | Показ, согласование дизайна, GitHub Pages |
| **С сервером** | В базе PostgreSQL на сервере — общие для всех | Настоящий магазин |

Режим выбирается адресом API в `frontend/env.js` (`''` — локальное хранилище без начальных товаров, `'/api'` — сервер на этом же домене). Отдельная демонстрация с примерами собирается только через `demo/`. При деплое файл подставляется автоматически.

План запуска с проверками и откатом — [18-Запуск-за-час.md](18-Запуск-за-час.md). Час реалистичен, если сервер, DNS, почта и каталог подготовлены заранее.

**Коротко, где какие настройки:**

| Где запускаем | Файл настроек | Что делать |
|---|---|---|
| Свой компьютер | **не нужен** | всё работает по умолчанию: база-файл `backend/dev.db`, администратор `admin@demo.kz` / `admin12345`, коды из писем — в `backend/dev-mail.log` |
| Свой сервер (VPS, Docker) | **`deploy/.env`** (образец `deploy/.env.example`) | один файл: домен, пароль базы, администратор, почта, Kaspi |
| Render | панель Render → Environment | те же переменные, что в `deploy/.env.example` |

Пароли живут только в `deploy/.env` на сервере (или в панели Render). В git, в ответы API и в журналы они не попадают.
Если в рабочем режиме что-то заполнено небезопасно (короткий пароль, нет `SECRET_KEY`, почта администратора не задана…), **сервер не запустится** и напишет в журнале, что исправить.

## Что умеет сервер

- **Аккаунты:** регистрация с подтверждением почты кодом, вход по паролю, вход по коду из письма, вход через Google, выход (и «выйти на всех устройствах»), «Забыли пароль?», смена пароля, удаление аккаунта.
- **Администратор один** — почта и пароль только в `deploy/.env` (`ADMIN_EMAIL`, `ADMIN_PASSWORD` или `ADMIN_PASSWORD_HASH`). Сменить пароль: поменять там и перезапустить сервер.
- **Каталог, отзывы, заказы, тексты и фото сайта** — в базе PostgreSQL; сумму заказа считает сервер по ценам из базы.
- **Оплата:** перевод на Kaspi (работает сразу), наличные, готовый к включению Kaspi Pay — см. [14-Платежи.md](14-Платежи.md).
- **Защита:** см. [15-Безопасность.md](15-Безопасность.md).
- **Админка → Настройки → «Готовность к запуску»** показывает, что на сервере настроено, а чего не хватает (без показа самих паролей).

## Запуск на своём компьютере

Нужен только Python 3.11+. Никаких `.env`, PostgreSQL и Docker.

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate                 # Windows;  macOS/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
```

При первом запуске сервер создаёт базу `backend/dev.db` и добавляет только категории. Товары добавляются через админку; необязательный импорт примеров находится в `demo/seed_backend.py`.
Вход в админку: `admin@demo.kz` / `admin12345`. Коды из писем — в окне сервера и в `backend/dev-mail.log`.
Начать с чистой базы: удалите `backend/dev.db` и перезапустите.

Сайт: `python deploy/serve_frontend.py` (из корня проекта, адрес http://localhost:5174); чтобы он работал с сервером, временно впишите в `frontend/env.js` адрес `'http://localhost:8000/api'`.

Тесты: `python -m pytest` в папке `backend` (функциональные + тесты безопасности).
Проверка настроек: `python -m app.cli check`.

## Вариант 1. Свой сервер (VPS) с Docker — рекомендуемый

На одном сервере работают: сайт (Nginx), API (FastAPI), **база PostgreSQL**, продление HTTPS и ежедневные резервные копии базы.
Нужен VPS с Ubuntu, Docker Compose v2, Git и Python 3.11+. Для PostgreSQL и двух процессов API разумно начать с 2 ГБ памяти. Домен должен указывать на IP сервера (A-записи для `домен` и `www.домен`); если есть AAAA-записи, они тоже должны вести на этот сервер. Откройте входящие TCP 80/443 и разрешите исходящую почту SMTP 587 у хостера. Сертификат выпускается сразу для обоих имён, поэтому до шага 5 оба должны отвечать с VPS.

```bash
# 1. Docker
curl -fsSL https://get.docker.com | sh

# 2. Код
git clone https://github.com/<логин>/<репозиторий>.git shop && cd shop

# 3. Настройки — один файл
umask 077
cp deploy/.env.example deploy/.env
nano deploy/.env                         # заполнить строки «← ОБЯЗАТЕЛЬНО»
python3 -c "import secrets; print(secrets.token_urlsafe(48))"   # → SECRET_KEY
python3 -c "import secrets; print(secrets.token_hex(16))"       # → POSTGRES_PASSWORD

# 4. Публичные файлы сайта (папка .public/)
python3 deploy/prepare_frontend.py
docker compose --env-file deploy/.env -f deploy/docker-compose.yml config --quiet
docker compose --env-file deploy/.env -f deploy/docker-compose.yml build backend
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps backend python -m app.cli check

# 5. HTTPS-сертификат (один раз)
docker compose --env-file deploy/.env -f deploy/docker-compose.yml --profile init run --rm --service-ports certbot-init

# 6. Запуск
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs -f backend        # убедиться, что запустился (Ctrl+C — выйти)

# 7. Стартовые категории (товары добавляются через админку)
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec backend python -m app.cli seed --frontend /frontend
```

Сайт — `https://<домен>`, API — `https://<домен>/api`. Схема базы создаётся и обновляется сама при каждом запуске (миграции Alembic).

**Проверить настройки** (что заполнено, чего не хватает):

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm backend python -m app.cli check
```

**Пароль администратора без хранения в открытом виде** (по желанию):

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps backend python -m app.cli hash-password
```

Строку `ADMIN_PASSWORD_HASH='…'` вставьте в `deploy/.env`, `ADMIN_PASSWORD` оставьте пустым, перезапустите: `docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d backend`.

**Обновление сайта:**

```bash
git pull && python3 deploy/prepare_frontend.py && docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
```

### База данных на сервере

- PostgreSQL 16 работает в контейнере `db` во **внутренней сети без доступа из интернета** — порт базы наружу не открыт.
- Данные лежат в томе Docker `pgdata` и переживают перезапуск и обновления.
- Пароль базы — `POSTGRES_PASSWORD` в `deploy/.env`; адрес подключения для API собирается автоматически.
- **Резервные копии:** контейнер `backup` сразу после запуска и затем раз в сутки сохраняет базу в `deploy/backups/kbch-ДАТА.dump` и фото в `media-ДАТА.tgz`. После успешного создания пары удаляет копии старше `BACKUP_KEEP_DAYS` дней; при ошибке старые остаются. Это не синхронный снимок: перед важным обновлением остановите API и снимите пару вручную. Копируйте `deploy/backups/` ещё и за пределы VPS: потеря диска сервера уничтожит локальные копии.
- Certbot проверяет продление дважды в сутки, Nginx перечитывает сертификат каждые 6 часов. Проверка после первого запуска: `docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec web nginx -t`. Пробное продление без смены сертификата: `docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --entrypoint certbot certbot renew --webroot -w /var/www/certbot --dry-run`.

Копия прямо сейчас:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T backup sh -c 'umask 077; pg_dump -Fc -f /backups/kbch-manual.dump && tar czf /backups/media-manual.tgz -C /media . && pg_restore --list /backups/kbch-manual.dump >/dev/null && tar tzf /backups/media-manual.tgz >/dev/null'
```

Восстановление из копии (заменяет текущие данные!):

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml stop backend
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T backup sh -c 'pg_restore --exit-on-error --clean --if-exists -d "$PGDATABASE" /backups/kbch-2026-10-14_030000.dump'
docker compose --env-file deploy/.env -f deploy/docker-compose.yml start backend
```

Загруженные фото хранятся в томе `media` (по умолчанию `kbch_media`). Для полного восстановления нужна соответствующая копия фото: сначала остановите API, распакуйте выбранный `media-…tgz` в этот том и затем запускайте API. Перед заменой снимите текущую копию; не выполняйте `docker compose down -v` — эта команда удаляет базу, фото и сертификаты. Пошаговый откат — в [18-Запуск-за-час.md](18-Запуск-за-час.md).

## Вариант 2. Render (без своего сервера)

1. Зарегистрируйтесь на [render.com](https://render.com) и подключите GitHub.
2. **New → Blueprint →** выберите репозиторий. `render.yaml` предлагает **платные** API (`0.5c-512mb`), PostgreSQL (`0.1c-256mb`, диск 5 ГБ) и диск фото 1 ГБ; статический сайт не требует вычислительного тарифа. Перед подтверждением проверьте текущую месячную стоимость в Render. Данные ресурсов создаются только после вашего подтверждения. `SECRET_KEY` генерируется сам. База доступна API во внутренней сети; внешние подключения закрыты.
3. **kbch-api → Environment** — заполните переменные (их смысл — в `deploy/.env.example`):
   `FRONTEND_URL` = адрес сайта, `PUBLIC_API_URL` = адрес API + `/api`, `CORS_ORIGINS` = адрес сайта, администратор, почта, Kaspi.
4. **kbch-site → Environment** — `API_URL` = адрес API + `/api`, затем **Manual Deploy**.
5. Откройте админку и создайте категории, реальные товары и загрузите фото. Контейнер Render собирается только из `backend/`, поэтому `python -m app.cli seed` без файла `frontend/js/data/categories.js` здесь неприменим; на VPS этот файл доступен через том `/frontend`. Демо-каталог в production сам не переносится.
6. После загрузки фото перезапустите API в Render и убедитесь, что оно осталось. `MEDIA_DIR=/app/media` совпадает с точкой постоянного диска. Проверьте восстановление PostgreSQL из панели и снимки media-диска, настройте отдельную внешнюю копию перед приёмом реальных заказов.

Бесплатный Render API не поддерживает постоянный диск и теряет загруженные фото при рестарте, а бесплатный PostgreSQL истекает через 30 дней. Поэтому он не используется в production-шаблоне. Актуальные ограничения и имена планов: [Render Blueprint](https://render.com/docs/blueprint-spec), [постоянные диски](https://render.com/docs/disks), [бесплатный тариф](https://render.com/docs/free). Постоянный диск означает короткую остановку API при обновлениях и одну его копию.

## Вариант 3. GitHub Pages (только сайт)

GitHub Pages публикует отдельную демонстрацию из `demo/.public/`, без рабочего API. Данные, фото, настройки и реализация workflow находятся в `demo/`; файл `.github/workflows/pages.yml` только запускает её. Инструкция запуска и удаления в два действия — в [demo/README.md](../demo/README.md). Основной магазин собирается независимо через `deploy/prepare_frontend.py` для VPS или Render.

## Вход через Google

1. [console.cloud.google.com](https://console.cloud.google.com) → создайте проект.
2. **APIs & Services → OAuth consent screen** — название магазина и почта.
3. **Credentials → Create credentials → OAuth client ID → Web application.**
4. **Authorized redirect URIs:** `https://<домен>/api/auth/google/callback`.
5. Client ID и Client secret → `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` в `deploy/.env`, перезапустите сервер.

## Письма с кодами (Gmail)

`SMTP_USER` — адрес Gmail, `SMTP_PASSWORD` — **пароль приложения** (аккаунт Google → Безопасность → Двухэтапная аутентификация → Пароли приложений). Обычный пароль Gmail не подойдёт.

## Если что-то не работает

| Признак | Где смотреть |
|---|---|
| Сайт не открывается | `docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps` — все ли контейнеры `running` |
| API не запускается | `docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs backend` — сервер пишет, какие настройки исправить |
| Не приходят письма | `SMTP_USER`, `SMTP_PASSWORD` (пароль приложения), админка → Настройки → «Готовность к запуску» |
| «Слишком много попыток» | сработала защита от перебора; подождать минуту (лимиты — `RATE_*` в `deploy/.env`) |
