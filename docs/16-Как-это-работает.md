# 16. Как это работает: технологии и методы простыми словами

Этот раздел объясняет **как и каким способом** сделана каждая часть магазина — без знания программирования.
Сложные слова объяснены в [словаре](10-Словарь.md), схемы — в [архитектуре](12-Архитектура.md).

---

## 1. Сравнение с обычным магазином

| В обычном магазине | На сайте | Где в проекте |
|---|---|---|
| Витрина и зал, где ходят покупатели | **Фронтенд** — страницы в браузере | `frontend/` |
| Продавец за прилавком: принимает заказ, проверяет, считает сумму | **API (бэкенд)** — программа на сервере | `backend/app/` |
| Склад и учётная книга | **База данных PostgreSQL** | на сервере, `backend/app/db/` |
| Охранник на входе | **Nginx** — принимает всех посетителей, пускает дальше, отсекает лишних | `deploy/nginx/` |
| Сейф с ключами | **Файл настроек `.env`** — пароли и ключи | `deploy/.env` (только на сервере) |
| Касса и терминал | **Способы оплаты** (Kaspi, наличные) | `backend/app/services/payments/` |

Покупатель видит только витрину. Всё важное — цены, заказы, пароли, права — решает «продавец» на сервере, поэтому обмануть магазин из браузера нельзя.

## 2. Из чего сделано (технологии)

| Часть | Технология | Почему выбрана |
|---|---|---|
| Страницы | **HTML + CSS + JavaScript без фреймворка** | Простые файлы без сборки: открываются сразу, легко править, быстро грузятся |
| Сервер | **Python + FastAPI** | Современный, быстрый, сам проверяет входящие данные и сам пишет документацию API |
| База данных | **PostgreSQL** | Надёжная бесплатная база, стандарт для интернет-магазинов |
| Работа с базой | **SQLAlchemy** (ORM) + **Alembic** (миграции) | Запросы к базе пишутся на Python, а не склеиваются текстом — это и удобно, и защищает от SQL-инъекций |
| Пароли | **bcrypt** | Специальный медленный алгоритм хеширования паролей — его очень долго подбирать |
| Письма | **SMTP** (например, Gmail) | Обычная почта: коды подтверждения приходят как письмо |
| Вход через Google | **OAuth 2.0 / OpenID Connect** | Стандарт входа «через аккаунт Google»: пароль от Google сайт не видит |
| Запуск на сервере | **Docker + Docker Compose** | Всё (база, сервер, Nginx) запускается одной командой одинаково на любом сервере |
| Веб-сервер | **Nginx** | Быстро отдаёт страницы и картинки, включает HTTPS, ограничивает запросы |
| HTTPS | **Let's Encrypt (certbot)** | Бесплатный сертификат, продлевается сам |
| Тесты | **pytest** (сервер), **node:test** (сайт), **Chrome** (проверка в браузере) | Автоматическая проверка, что ничего не сломалось |

## 3. Как работает каждая функция

### Открытие страницы

1. Браузер получает HTML-файл — это «каркас» без текста.
2. Подключается один файл `js/app.js` — **загрузчик**. Он по очереди подключает остальные скрипты: настройки, тексты, хранилище, компоненты, логику страницы.
3. В режиме с сервером загрузчик одним запросом `/api/bootstrap` получает всё сразу: кто вошёл, каталог, отзывы, заказы, тексты. Это быстрее, чем десять отдельных запросов.
4. Тексты подставляются в каркас по меткам `data-t="home.hero.title"` из файлов `texts/ru/`.
5. Смотреть сайт может любой посетитель. На оформление заказа, в личный кабинет и админку гость попадает только после входа: `core/auth-guard.js` отправляет его на вход и затем возвращает обратно.

**Метод:** многостраничный сайт (каждая страница — свой HTML) + общий загрузчик + один запрос за данными.

### Демо-режим и режим с сервером

Все страницы берут и меняют данные только через одно место — **хранилище `App.db`** (`js/store/`).
- В демо-режиме хранилище пишет в память браузера (`localStorage`).
- С сервером файл `js/store/remote.js` подменяет методы хранилища: каждое изменение уходит на сервер.

Страницам всё равно, где лежат данные, поэтому один и тот же сайт работает в обоих режимах. Переключатель — одна строка в `env.js`.
**Метод:** «адаптер» — одна точка доступа к данным с заменяемой реализацией.

Демо-наполнение и быстрый вход в демо-аккаунты подключаются только на своём компьютере (`localhost`) и на GitHub Pages (проверка адреса в `js/app.js`). На настоящем домене магазина их нет.

### Регистрация и подтверждение почты

Регистрация нужна **только для покупки**: смотреть товары, читать отзывы и собирать корзину можно без аккаунта. Когда гость нажимает «Оформить заказ», сайт просит войти или зарегистрироваться и затем возвращает к оформлению.

1. Покупатель вводит имя, почту и пароль.
2. Сервер проверяет пароль: не короче 8 символов, не из списка частых («12345678», «password»…), не содержит часть почты.
3. Пароль превращается в **хеш bcrypt** и только так сохраняется.
4. Сервер создаёт **6-значный код**, отправляет его письмом, а в базе хранит не сам код, а его **HMAC-отпечаток**.
5. Код действует 10 минут, ввести можно 5 раз, повторно отправить — не чаще раза в минуту.
6. Верный код → почта подтверждена → покупатель сразу входит.

**Метод:** подтверждение владения почтой одноразовым кодом (OTP).

### Как хранятся пароли (bcrypt)

Пароль никогда не хранится в открытом виде. Хранится **хеш** — «отпечаток», из которого пароль восстановить нельзя.
- При входе введённый пароль снова превращается в отпечаток и сравнивается с сохранённым.
- К каждому паролю добавляется случайная **соль**, поэтому у двух людей с одинаковым паролем отпечатки разные.
- bcrypt специально медленный (12 «раундов»): одна проверка — доли секунды для человека, но перебор миллионов паролей занял бы годы.

### Вход и «запоминание» пользователя (сессия)

1. После входа сервер выдаёт **токен** — длинную случайную строку (43 символа).
2. Браузер хранит токен и прикладывает его к каждому запросу в заголовке `Authorization: Bearer …`.
3. В базе хранится не токен, а его **SHA-256 отпечаток**. Даже укравший базу не сможет войти.
4. Вход действует 30 дней. «Выйти» удаляет сессию; «Выйти на всех устройствах» — все сессии; смена пароля завершает все остальные сессии.

**Метод:** токен-аутентификация (bearer token). Cookie не используются — поэтому атака CSRF невозможна.

### Вход по коду из письма и через Google

- **По коду:** почта → письмо с кодом → ввод кода. Если такой почты нет — аккаунт создаётся сам.
- **Через Google:** сайт отправляет покупателя на страницу Google → Google спрашивает разрешение → возвращает на сервер подтверждённую почту и имя. Сервер проверяет подписанный параметр `state` (защита от подделки) и выдаёт свой токен. Пароль от Google магазин не видит.

**Метод:** OAuth 2.0 Authorization Code + OpenID Connect.

### Администратор

- Администратор **один**, его почта и пароль (или хеш пароля) записаны только в `deploy/.env` на сервере.
- При каждом запуске сервер создаёт этот аккаунт или обновляет ему пароль; у всех остальных роль администратора снимается.
- Каждая операция админки (`/api/admin/…`, изменение товаров, текстов) проверяет роль **на сервере**. Скрыть кнопку на сайте недостаточно — поэтому проверка именно на сервере.

**Метод:** ролевая модель доступа (роли «покупатель» и «администратор»).

### Каталог и товары

- Товар хранится в таблице `products`: часто используемые поля (цена, остаток, статус, категория) — отдельными колонками, всё остальное (описание, состав, применение, фото, свои разделы) — в поле `data` в формате JSON.
- Поэтому администратор может добавлять новые разделы карточки без изменения базы.
- Адрес товара — **slug** (`anua-heartleaf-77-soothing-toner`), он создаётся из названия и всегда уникален.
- Фото из админки отправляются на сервер; сервер проверяет **по содержимому файла**, что это действительно JPG/PNG/WEBP, и сам придумывает имя файла.

### Корзина и заказ

1. Корзина и избранное хранятся в браузере покупателя — их не нужно отправлять на сервер до оформления.
2. При оформлении браузер отправляет **только номера товаров и количество — без цен**.
3. Сервер сам берёт цены из базы, проверяет наличие, **блокирует строку товара** на время заказа (чтобы два покупателя не купили последнюю штуку одновременно), списывает остаток, считает доставку и итог.
4. Номер заказа — порядковый: 1001, 1002…
5. Отмена заказа администратором возвращает товары на склад.

**Метод:** сервер — единственный источник правды о ценах и остатках.

### Оплата

Каждый способ оплаты — отдельный небольшой файл с одинаковым набором действий («начать оплату», «показать инструкцию»). Список включённых способов задаётся в `.env`.

- **Перевод на Kaspi:** покупатель видит номер, получателя, сумму и комментарий «Заказ №…»; администратор отмечает «Оплачен».
- **Наличные:** оплата при получении.
- **Kaspi Pay:** сервер создаёт счёт через API Kaspi; Kaspi присылает **уведомление (webhook)** об оплате. Уведомление принимается только с верной **подписью HMAC** и если сумма совпадает с заказом.

**Метод:** шаблон «стратегия» — новый способ оплаты добавляется новым файлом, остальной код не меняется. Подробно — [раздел 14](14-Платежи.md).

### Отзывы

- Отзыв может оставить вошедший покупатель, один на товар (повторный — изменяет первый).
- Если покупатель заказывал этот товар — у отзыва отметка «Покупка подтверждена».
- «Полезно» — один голос от человека (у гостя — по случайному номеру браузера).
- Администратор отвечает, скрывает или удаляет отзывы.

### Тексты и фото сайта из админки

- Все тексты лежат в `texts/ru/*.js` (по файлу на раздел). В админке их можно изменить — правки хранятся отдельно и накладываются поверх.
- В правках разрешены только простые теги (`<b>`, `<i>`, `<br>`, `<small>`), всё остальное сервер и браузер превращают в обычный текст — так через тексты нельзя вставить вредный скрипт.
- Сайт готов к другим языкам: достаточно скопировать `texts/ru` в `texts/kk` и перевести.

### Адаптивность (телефон, планшет, 2K, 4K)

- Один и тот же HTML; оформление меняется **медиазапросами CSS** («если экран уже 760 px — так»).
- Стили для разных устройств разложены по папкам `css/responsive/phone`, `tablet`, `desktop`, `touch`.
- Для сенсорных экранов увеличены зоны нажатия; для тех, кто отключил анимации в системе, анимации выключаются.

### Анимации

- Появление блоков при прокрутке — **IntersectionObserver** (браузер сообщает, когда блок попал на экран).
- Плавные переходы между страницами — встроенная в браузер технология **View Transitions**.

## 4. База данных

| Таблица | Что хранит |
|---|---|
| `users` | покупатели и администратор: почта, имя, хеш пароля, роль |
| `sessions` | активные входы (отпечатки токенов, срок) |
| `email_codes` | отпечатки кодов из писем, срок, число попыток |
| `categories` | категории и подкатегории |
| `products` | товары |
| `reviews`, `review_votes` | отзывы и голоса «полезно» |
| `orders` | заказы: состав, суммы, доставка, статус, оплата |
| `site_settings` | правки текстов и заменённые фото сайта |

- **Связи:** заказ и отзыв ссылаются на пользователя; при удалении аккаунта его сессии удаляются, а заказы остаются (магазину нужна история).
- **Ограничения в самой базе:** цена и остаток не могут быть отрицательными, оценка — только 1–5, роль и статусы — только из списка. Даже ошибка в коде не запишет неправильные данные.
- **Миграции (Alembic):** структура базы описана в коде; при обновлении сервер сам применяет изменения («миграции») к базе, не теряя данных.
- **Резервные копии:** раз в сутки полная копия базы сохраняется в `deploy/backups/`, старые удаляются через 14 дней.

## 5. Защита (коротко)

Подробно — [раздел 15](15-Безопасность.md).

| Угроза | Способ защиты |
|---|---|
| Подбор пароля | ограничение попыток с одного адреса и на один аккаунт, медленный bcrypt |
| SQL-инъекция | запросы к базе только с параметрами (через SQLAlchemy) |
| XSS (чужой скрипт) | очистка HTML, экранирование, политика CSP |
| DDoS / флуд | лимиты в Nginx и в API, ограничение размера запроса |
| Кража базы | в базе только отпечатки паролей, токенов и кодов |
| Подмена цены | сумму считает сервер |
| Перехват данных | только HTTPS |
| Утечка паролей из кода | все секреты только в `.env` на сервере |

## 6. Как магазин публикуется в интернете

1. На сервере (VPS) устанавливается Docker.
2. Заполняется один файл `deploy/.env`.
3. Одна команда запускает пять программ («контейнеров»): **база**, **API**, **Nginx**, **продление HTTPS**, **резервные копии**.
4. Nginx отдаёт страницы сайта из папки `.public/` (в неё попадают только публичные файлы — без документации и служебных файлов), запросы `/api/…` передаёт API, а фото — из папки загрузок.

Подробно — [раздел 11](11-Бэкенд-и-деплой.md).

## 7. Как проверяется качество

- **264 автоматических теста** ([tests/README.md](../tests/README.md)): функции, безопасность, база данных, заказы, логика сайта, публикация.
- В GitHub тесты запускаются сами при каждом изменении, сервер проверяется и на SQLite, и на настоящем PostgreSQL.
- Сайт проверялся в браузере Chrome: все страницы и разделы админки, в обоих режимах, под гостем, покупателем и администратором, на телефоне и компьютере, плюс сквозные сценарии «регистрация → заказ → оплата».
